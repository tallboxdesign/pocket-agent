# Rules Engine v2: OR Logic (Condition Groups) + Draft Reply Addressing

**Status:** Proposed
**Author:** EVA
**Date:** 2026-02-02

---

## 1. Executive Summary

Two enhancements to the rules engine:

1. **OR Logic via Condition Groups** -- The existing rules engine evaluates all conditions with AND logic (every condition must pass). This change introduces ConditionGroups, where each group can independently use AND or OR logic. Multiple groups are joined by outer AND. This enables rules like "label is Work OR label is Urgent, AND confidence >= high."

2. **Draft Reply Addressing** -- The current `draft_reply` action hardcodes the recipient to `email.sender` and the subject to `Re: ` + original subject. This change adds configurable addressing: reply-to/from/custom recipient selection, CC/BCC fields, subject prefix control, skip conditions for noreply and auto-generated emails, quoted original toggle, and max draft length.

Both features are backward-compatible. No data loss. Existing rules continue to work without modification.

## 3. Exact Schema Changes + Migration

### 3.1 TypeScript Type Changes

**New types** (add after L38 in `src/scheduler/rules-engine.ts`):

```typescript
export interface ConditionGroup {
  mode: 'AND' | 'OR';
  items: Condition[];
}
```

**No changes** to `Condition`, `Action`, `EmailRule`, or `EmailContext` interfaces. The `conditions_json` column type remains `string` -- only the parsed shape changes.

### 3.2 SQLite Schema

No DDL migration required. The `conditions_json` column is `TEXT` and accepts any valid JSON. The new format is a superset that the read-time migration handles transparently.

### 3.3 Read-Time Migration (Automatic)

When parsing `conditions_json`, detect the old format and wrap it:

```typescript
function parseConditionGroups(raw: string): ConditionGroup[] {
  const parsed = safeJsonParse<unknown[]>(raw, []);
  if (parsed.length === 0) return [];

  // Old format: array of {type, value} without 'mode' field
  if (parsed.length > 0 && 'type' in (parsed[0] as Record<string, unknown>)) {
    return [{ mode: 'AND', items: parsed as Condition[] }];
  }

  // New format: array of {mode, items}
  return parsed as ConditionGroup[];
}
```

This function replaces every `safeJsonParse<Condition[]>(rule.conditions_json, [])` call. Locations:

- `matchConditions` (L383)
- `testRule` (L730)

On save, the UI always writes the new `ConditionGroup[]` format. Old rules are migrated transparently on first read and permanently on first edit-and-save.

### 3.4 Draft Reply Config Fields

No schema change. The `config: Record<string, string>` on the `Action` interface already supports arbitrary keys. New keys stored in `actions_json` for `draft_reply` actions:

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `replyTarget` | `'reply_to' \| 'from' \| 'custom'` | `'reply_to'` | How to determine the "To" address |
| `customTo` | `string` | `''` | Recipient email when `replyTarget = 'custom'` |
| `cc` | `string` | `''` | Comma-separated CC addresses |
| `bcc` | `string` | `''` | BCC addresses (see note below) |
| `bccInBody` | `'true' \| 'false'` | `'false'` | If true, prepend "BCC: {bcc}" line in draft body |
| `subjectPrefix` | `string` | `'Re: '` | Prefix prepended to original subject |
| `skipNoReply` | `'true' \| 'false'` | `'true'` | Skip if sender matches noreply patterns |
| `skipAutoGenerated` | `'true' \| 'false'` | `'true'` | Skip if Auto-Submitted or Precedence: bulk/list |
| `includeQuotedOriginal` | `'true' \| 'false'` | `'false'` | Append quoted original after draft body |
| `maxDraftLengthChars` | `string` (number) | `'3500'` | Truncate generated draft body to this length |

**BCC note:** The gog CLI `createDraft` does not support a `--bcc` flag. When `bccInBody` is true, a `BCC: addr@example.com` line is prepended to the draft body as a manual reminder. The user must move it to the BCC field before sending.

## 4. Backend Spec with Function Signatures

### 4.1 New / Modified Functions in `rules-engine.ts`

#### `parseConditionGroups` (new, module-level helper)

```typescript
function parseConditionGroups(raw: string): ConditionGroup[]
```

Replaces direct `safeJsonParse<Condition[]>` calls. Detects old vs new format.

#### `matchConditions` (modified, L382)

```typescript
private async matchConditions(rule: EmailRule, email: EmailContext): Promise<boolean>
```

New logic:
1. Parse `conditions_json` via `parseConditionGroups`.
2. For each group: if `mode === 'AND'`, all items must pass. If `mode === 'OR'`, any item must pass.
3. Outer logic: all groups must pass (AND across groups).
4. `thread_state` conditions within any group still use async `getOrFetchThreadState`.

#### `matchConditionGroup` (new, private)

```typescript
private async matchConditionGroup(group: ConditionGroup, email: EmailContext): Promise<boolean>
```

Evaluates a single group. Handles both sync (`matchSingleCondition`) and async (`thread_state`) conditions.

#### `testRule` (modified, L726)

```typescript
testRule(ruleId: number, limit?: number): TestResult[]
```

New return type:

```typescript
interface GroupTestResult {
  mode: 'AND' | 'OR';
  passed: boolean;
  conditions: { type: string; value: string; passed: boolean }[];
}

interface TestResult {
  email: { subject: string; sender: string; label: string };
  matched: boolean;
  groups: GroupTestResult[];
  // Backward-compat flat view:
  conditions: { type: string; value: string; passed: boolean }[];
}
```

The flat `conditions` array is retained for backward compatibility with the UI render path. It is the concatenation of all group items.

#### `actionDraftReply` (modified, L535)

```typescript
private async actionDraftReply(email: EmailContext, config: Record<string, string>): Promise<void>
```

New flow:

```
1. Fetch thread via getThread(threadId, account)
2. Parse headers: Reply-To, From, Auto-Submitted, Precedence, List-Id
3. Check skipNoReply:
   - If sender matches /noreply|no-reply|do-not-reply|donotreply/i -> skip, log
4. Check skipAutoGenerated:
   - If Auto-Submitted header exists and != 'no' -> skip, log
   - If Precedence header is 'bulk' or 'list' -> skip, log
5. Determine recipient:
   - replyTarget='reply_to': use Reply-To header, fallback to From
   - replyTarget='from': use From header
   - replyTarget='custom': use customTo value
   - If resolved recipient is empty -> throw error
6. Build subject: subjectPrefix + original subject (avoid double "Re: Re: ")
7. Build prompt via buildDraftReplyPrompt (pass includeQuotedOriginal flag)
8. Call glmFlash
9. Truncate body to maxDraftLengthChars
10. If bccInBody && bcc is set: prepend "BCC: {bcc}\n\n" to body
11. Call createDraft({ to: recipient, cc, subject, body, replyToMessageId, account })
12. Log addressing decisions to console
```

#### `parseEmailHeaders` (new, private helper)

```typescript
private parseEmailHeaders(threadJson: string): {
  replyTo: string | null;
  from: string;
  autoSubmitted: string | null;
  precedence: string | null;
  listId: string | null;
}
```

Parses the thread JSON returned by `getThread()`. Extracts headers from the first (or most recent, depending on thread structure) message.

#### `isNoReplyAddress` (new, module-level helper)

```typescript
function isNoReplyAddress(email: string): boolean
```

Returns true if the email matches common noreply patterns: `noreply@`, `no-reply@`, `do-not-reply@`, `donotreply@`, `mailer-daemon@`.

## 6. Failure Scenarios with Recovery

### 6.1 OR Logic Failures

| Scenario | Detection | Recovery |
|----------|-----------|----------|
| Old-format `conditions_json` read | `parseConditionGroups` detects array of `{type,value}` objects without `mode` field | Auto-wrap in `[{ mode: 'AND', items: [...] }]`; log migration at debug level |
| Corrupted `conditions_json` (invalid JSON) | `safeJsonParse` returns `[]` | Rule has no conditions, matches all emails (same as current behavior); log warning |
| Empty group (no items) | Group has `items: []` | Passes trivially (AND of nothing = true, OR of nothing = false); document this edge case |
| OR group with zero passing conditions | Normal evaluation | Group fails; outer AND fails; rule does not fire |
| All groups empty | All groups pass trivially | Rule matches all emails (same as no-condition rule); UI shows "no conditions" summary |

### 6.2 Draft Reply Addressing Failures

| Scenario | Detection | Recovery |
|----------|-----------|----------|
| Reply-To header missing | `parseEmailHeaders` returns `replyTo: null` | Fall back to From header; log `[RulesEngine] No Reply-To header, using From: {addr}` |
| From header also missing | `from` is empty string | Throw error; log `[RulesEngine] Cannot determine recipient for draft reply`; execution logged as `error` |
| noreply sender detected | `isNoReplyAddress` returns true and `skipNoReply` is true | Skip action entirely; log `[RulesEngine] Skipped draft_reply: noreply sender {addr}` |
| Auto-generated email detected | Auto-Submitted or Precedence header check | Skip action entirely; log `[RulesEngine] Skipped draft_reply: auto-generated email` |
| GLM returns empty content | `glmRes.content?.trim()` is falsy | Throw error `GLM returned empty draft content`; do NOT create draft |
| GLM returns content exceeding max length | `body.length > maxDraftLengthChars` | Truncate body at `maxDraftLengthChars`; append `\n\n[Draft truncated]` |
| Thread fetch fails | `getThread` returns `success: false` | Log warning; fall back to `email.sender` as recipient (current behavior) |
| Custom recipient is invalid email | Cannot validate at rule-save time (string field) | gog CLI will fail; error propagates to execution log |
| Subject already starts with prefix | `subject` starts with "Re: " and `subjectPrefix` is "Re: " | Strip existing prefix before prepending to avoid "Re: Re: Re: ..." |
| `createDraft` gog CLI call fails | `createDraft` returns `{ success: false }` | Throw error with gog stderr; logged as execution error |

### 6.3 Test Mode Failures

| Scenario | Detection | Recovery |
|----------|-----------|----------|
| Test with OR group + thread_state condition | `matchSingleCondition` uses cache-only lookup (L782-788) | If no cache entry exists, condition returns false; test UI shows "(no cache)" annotation |
| Test with no processed emails | `email_processing_state` table is empty | UI shows "No emails to test against" |
| Test result has mixed old/new group format | `testRule` always outputs new group format | UI always renders group format; flat `conditions` array provided for backward compat |
